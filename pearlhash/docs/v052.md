# v0.0.52: four-row packed B reconstruction (offline GPU experiment)

v051 remains the preferred live development path. Its latest five-minute rig
run completed 173944832 tiles, 23 nonces started, 19 full nonces and 42467
lean-direct windows, with clean joined shutdown and WildRig restart. No share
was submitted; 20 status acknowledgements are not accepted shares.

PTX inspection found that the compiler already reused B permutation loads
between the two eight-column fragments. This experiment changes the deeper
representation: reconstruct four B rows together with independent modulo-256
byte arithmetic, then warp-shuffle the packed results into the existing MMA
fragment order. Producer lane low four bits select K; its high bit selects a
four-row block. The two K halves and two column halves produce four packed
words. Destination group/thread/byte selects the source lane and byte needed
by the established B fragment ABI.

b_quad.h prevents subtraction borrow and fill-add carry from crossing byte
boundaries. It computes exactly (64 + signed_a - signed_b) & 255 for each lane.
Original coalesced global coefficient reads stage the same 16 by 128 signed
coefficients into shared memory, regrouped as four-byte words. Two entries test
strides of four versus five words per rank index: quad4 uses 16384 shared bytes
per CTA; quad5 uses 20480 with padding. Both retain eight warps/256 threads,
one query per warp and warp-only synchronization. No CTA barriers are added.

Static PTX inspection: B reconstruction changes eight permutation loads to two,
32 shared byte-load instructions to eight shared word loads, and adds sixteen
warp shuffles per loop step. This changes instruction organization, not a
measured bandwidth or speed claim. Physical registers/local/shared memory are
queried from the driver JIT outside benchmark timing. Runtime wins are unknown
until the rig comparison; new shuffles and layout/occupancy tradeoffs may lose.

A fragment loads and the body from mma_accumulate through transcript folding,
keyed hash, target comparison, atomic queue and generation fields are verbatim
the validated direct scanner. Maps, target, nonce and proof rules are unchanged.
Both entries retain the 24-argument ABI. Python changes only select the new
function within the established lean dispatch: stream reset, scalar queue
validation, every guard and independent CPU candidate checks are retained.

Preflight compares both layouts against actual lean v051 dispatch on four full
4096-query windows each (first, row crossing, middle, end). It requires sixteen
independent CPU transcript samples, 36 target/queue cases, two populated 67-query
overflows, 56 deliberate global guard corruptions with fresh dispatches, two
fresh V3 proofs passed by the official CPU verifier, retained odd miss windows
and stale rejection. It records each JIT kernel's resource use. Only complete
success enables timing. Shared staging/layout/shuffles still require hardware
validation; host equivalence alone does not establish GPU correctness.

One fresh synthetic production nonce/target and identical ranges compare
lean-direct-v051, quad4-v052 and quad5-v052. All use advance(4096). Twenty-four
rounds repeat all six orders four times, 65536 tiles/mode/round. Initial context/
JIT and shared commitment/nonce prep are excluded; cache/setup cost is reported.
Primary timings are uninstrumented. Separate diagnostics require all three
modes to retain 16 async resets, 32 kernel launches, 16 stream waits and 16
readbacks (8064 bytes), with zero window host uploads/context-wide waits.
Adoption requires >3% elapsed-time reduction. Output: B QUAD COMPARISON,
DRIVER COUNTS and KERNEL RESOURCES; b-quad-comparison.json saves the full result.

73 host tests pass. Actual C++ helpers exhaust all 65536 byte-value pairs in
all four byte lanes with contrasting neighboring values; 2048 fragment mappings
across every lane, K/column half, offsets and both strides match cached_b_word.
Tests also check unchanged A/MMA/hash/queue source, both 24-slot PTX entries,
entry selection/lean driver calls, stale cursor cleanup, scalar/queue/guard/
planner regressions, balanced comparison and installer correctness gates.

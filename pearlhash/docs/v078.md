# v078: two independent ways to put more work into the validated scanner

This release tests the next two requested targets independently against the retained wide16k baseline. It does not combine them or assume their gains multiply. It is an offline correctness, speed and GPU-board energy suite. No new pool connection or share submission is made.

## Target 1: more reuse within a block

Sixteen consumer warps share one B column axis and an eight-step fragment buffer instead of eight warps. Each warp still has four tiles' accumulator/transcript state. This differs from the rejected eight-tiles-per-warp packing experiment. The first eight warps produce distinct B steps; all sixteen consumers participate in validation and every block barrier. Uniform-cache loading is distributed over 512 threads. At a full block the B reconstruction is shared across 64 rather than 32 tiles, halving reconstruction per canonical tile. This is a work-count saving, not a throughput prediction. Lower block scheduling flexibility, register allocation and barrier costs may erase it.

A source-equality test restricts changes to block size, row-group traversal, producer stride and uniform loading stride. The six MMA instructions per K32 step, eight-step staging, accumulator order, K128 cumulative checkpoints, A pointer bounds, transcript fold/emission, target and candidate queue semantics are unchanged. The 256-thread control PTX entry is byte-identical to v075. Both entries retain the same 24 arguments. Shared input arrays remain 3,072 + 4,096 = 7,168 bytes. Native register/local/shared/residency resources require the rig.

## Target 2: larger dispatches

The 32K and 64K modes use the exact unchanged control kernel with mode-sized guarded descriptor, target, candidate and audit buffers. The common seven-argument guard collector preserves status, generation/window identity and all 28 guard endpoints but accepts up to 65,536 queries. Per-mode host validation rejects batches/capacities above that mode's extent. Complete queue retries and independent CPU verification remain required before cursor credit.

The driver diagnostic for one 1,048,576-tile window requires respectively 64/32/16 resets, waits and 504-byte readbacks for 16K/32K/64K dispatches, with twice as many kernel launches (scanner plus guard collector), no HtoD copies and no context-wide waits. Thus batch sizes are checked through actual driver calls rather than inferred from labels. Larger dispatches may improve amortisation and scheduling waves; no gain is assumed.

## Correctness and fair work sets

Four independent preflights run before timing. Each compares two fresh production nonces and eight audited transcript windows against v070 in canonical-ID order. Windows use the mode's full limit, including 32K/64K transcripts. Sixteen samples per mode are independently checked by CPU matrix math. Gates also cover target cases, populated partial overflow, full-limit zero-capacity overflow (the full returned count must equal the mode's limit), malformed row/column maps, all 28 guard faults, retained/stale work and two fresh V3 proofs checked by the official CPU verifier. All four modes must pass before the benchmark starts.

Host tests exercise actual fully populated 16K/32K/64K queues, full retry/CPU crediting, allocation extents and mode-limit rejection. Compiled C++ helpers, under undefined-behaviour sanitizer, exhaust both complete 8,388,608-ID production bijections, inverse mappings and equal-work window identities. They exhaust collector count boundaries through 65,537 and guard/thread validity boundaries.

A 64-row group contains 1,048,576 canonical tiles. Benchmark windows are aligned whole groups, so both block traversals process identical canonical sets. Speed timing uses twelve rounds across two distinct nonces, six rounds per nonce, with 12,582,912 unique timed tiles per mode. Each nonce has a one-window warmup; the final nonce also contains a separate one-window driver diagnostic. No cursor runs past the 8,388,608-tile nonce domain. Four balanced mode orders put each mode in every position and cover every ordered neighbour once; they repeat three times. Initial setup and telemetry are excluded, setup is reported, and owners remain retained across nonces.

The blocks and batching groups are promoted separately, each requiring more than 3% median elapsed reduction against wide16k. A combined block/batch winner is not defined or reported. The installer validates both independent winner labels and the twelve-round equal-work result.

Energy measurements retain the v075-v077 read-only NVML sampler: 200 ms, two balanced rounds, one conditioning plus three measured full nonces per trial, 50,331,648 measured tiles per mode. Fresh nonce/A setup, search and cleanup are included; initial job/base/B/geometry preparation is excluded. Unsupported sensors leave speed usable and mark energy unavailable. These are approximate GPU-board measurements, not wall-plug power or live-pool efficiency; activity percentages do not establish Tensor Core saturation or achieved occupancy.

# v0.0.43: controlled full-search-loop comparison

Offline diagnostic, no changes to v040/v042 scanner/search implementations.
Uses one fresh synthetic production V3 job (5121 x 262144, K32768, rank128),
one GPU B commitment, one CPU-prepared nonce and identical target/seeds/mappings
in both paths. A deliberately tiny positive target avoids candidate/proof work;
any unexpected candidate fails the controlled comparison. No pool connection.

Constructs v040 new_cached_a_search and v042 DualSearch in the same CUDA context.
Both nonce caches remain resident throughout, so memory footprint does not vary
with scheduling order. Search/cache setup wall times are separately reported;
context/module loading and shared commitment/nonce preparation are excluded.
A 65536-tile warmup per mode precedes twenty alternating-order timing rounds.
Each round covers the same consecutive 65536 canonical tile IDs in both modes:
16 x advance(4096) for v040, 8 x advance(8192) for v042, matching live cadence.
Cursor continuity and identical global intervals are mandatory. Timed work is
1,310,720 unique tiles per mode; warmup and diagnostics are counted separately.

Primary wall measurements include the actual search.advance loops, descriptor
planning, uploads, launch/synchronization, queue readback, guard and generation
checks and cursor accounting. Exclude socket/heartbeat/status telemetry, proof
building, initial context/JIT and common job/nonce preparation. Backend prepare
and scan subtotals and per-round samples are saved. These component measurements
are not a mining hashrate or pool acceptance verdict. A >3% median improvement
is required to prefer two streams; the existing one-stream preference is kept
for smaller differences. Selection is advisory; no live path is changed.

After the uninstrumented timing rounds, a SEPARATE equal-range 65536-tile driver
count round reports API calls and transfer bytes for each mode. No timing hooks
wrap the primary rounds. This investigates a code difference: v040 initially
uses a one-record queue, while v042 allocates full query capacity and currently
reads every queue slot, even on misses. No optimization is applied in this
release, so the measurement compares the actual established implementations.
Counts show traffic in this process; they do not measure VRAM bandwidth
saturation, hardware occupancy, or prove a particular bottleneck.

Only owned search resources are freed; allocation leaks fail the run. Reports
contain aggregate timings/counters and synthetic tile ranges, not job headers,
seeds, nonces or wallet details. Output is created exclusively with mode0600.
Installer verifies pinned installed sources/PTX/library and completed v042
proof/live reports, without repeating old proof checks. Termius wrapper pauses
WildRig, schedules a 15-minute fallback restart, then restores it on completion.
XMRig, clocks and service configuration remain unchanged.

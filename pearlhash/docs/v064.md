# v0.0.64: four-tile B sharing and 40-row MMA packing

Three modes isolate the work reductions: unchanged v060 paired sharing, four-tile sharing with four padded 16-row slabs, and four-tile sharing with 40 canonical rows packed into three 16-row slabs. Per four tiles per K32 step, v060 reconstructs B twice and executes eight m16n8k32 operations. Both candidates reconstruct B once; the sharing control still executes eight operations, while packing executes six. These are work counts, not measured speedups. Shared-memory layout, exact signed int8/int32 arithmetic, cumulative checkpoints, keyed transcripts and target/queue handling remain established operations. v063 native XOR is deliberately excluded to keep this experiment isolated.

Quartet traversal uses `(row group, column, member)` order and maps each returned candidate back to its canonical row-major ID before proof construction. The 512 production row axes divide into 128 groups of four. Pack logical rows 0..39 in tile order into three slabs; positions 40..47 are zero. Each canonical tile retains a separate transcript: its row contributions may span slabs, but the per-checkpoint XOR includes exactly those ten rows and preserves its rotation/slot update. Incomplete quartet windows compute only valid axes and emit only requested queries. The host rejects row-axis counts not divisible by four before GPU allocations.

New preflight checks the exact bijection across 8388608 canonical tiles. For each candidate it compares four full 4096-query windows against actual v060, reassembling paired-order control output by canonical ID. Combined checks include eight windows, sixteen independent CPU transcript samples, thirty-six target/queue cases, two populated 67-query overflows, fifty-six deliberate guard faults, two fresh V3 proofs through the official CPU verifier, odd retained windows and stale rejection/cleanup. Every window retains all 28 guard endpoints and complete returned candidates retain independent CPU checking.

Only after all gates pass does the benchmark run 24 balanced rounds covering all six mode orders, 65536 tiles per mode per round, with 4096-tile advance calls and three caches resident in one context. Whole quartet-aligned windows cover exactly the same canonical sets in all modes. Primary timings are uninstrumented; a separate driver diagnostic requires 16 resets, 32 launches, 16 waits and 8064 downloaded bytes per mode. Registers/shared/local resources are reported. Additional accumulator/register pressure is a material risk. A variant is preferred only after more than 3% elapsed reduction versus v060; no live integration occurs.

The installer checks the already completed v060/v061 gates and 30 pinned dependency manifests. It excludes v062/v063 from PYTHONPATH and needs neither pending experiment to be run first. Readable sm_120 PTX is included: no CUDA toolkit or new native archive is installed on the rig. CPU library integrity is read from the installed verified v031 manifest. No wallet, live capture or real job/proof material is published.

`tools/run_v064.sh` verifies its pinned installer, schedules a 15-minute fallback before temporarily stopping WildRig, bounds execution to 780 seconds plus 15 seconds termination grace and explicitly starts WildRig on exit. It preserves CPU XMRig, clocks, permanent services/autostart and pools. This is offline only, with no pool connection, share submission or continuous custom miner.

Development validation: 73 targeted host tests passed. Actual shared C++ helpers pass exhaustive production mapping/work-set checks, real cached-A loader/zero-padding checks and randomized fold-partition checks. Host dispatch tests cover both kernels, complete overflow retries, canonical CPU-checked hits, all guards, partial quartets and stale reset/launch cleanup. NVRTC 12.9.86 builds reproduce byte-identical PTX; both entries have 24 arguments, no CTA barriers, and the expected eight/six MMA instructions. GPU correctness, fresh verifier execution and speed remain pending the rig run.

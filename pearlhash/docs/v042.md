# v0.0.42: bounded live cached-A two-stream worker

Uses unchanged rig-validated v040 GPU scan PTX and v039 GPU B commitment PTX,
plus v041 StreamDispatch. The rig's v041 offline comparison found about 8.2%
higher full-window component throughput with two streams. This is not a promise
of an equal live improvement or a memory bandwidth measurement.

DualSearch scans contiguous pairs of up to 8192 canonical tile IDs, split into
at most two nonempty <=4096-query intervals. Each lane has a separate descriptor,
target, status, full-capacity candidate queue and transcript allocation. Noise
and the 160 MiB production A cache are shared read-only. All staging completes
before both launches; both streams finish before readback. Every returned
candidate is independently CPU checked. Full queue capacity equals query count,
so a legitimate hit set cannot overflow. Any incomplete/malformed result fails
the pair; it is not credited. Global IDs add each lane's interval start, and the
lowest candidate from the complete pair is selected for proof.

Generation is checked before staging, before each launch, after both waits,
after each CPU candidate check and before cursor credit. A stale job, launch
error, queue failure or CPU mismatch closes the nonce resources. All in-flight
kernels are drained before shared inputs are freed. Both streams' results must
be complete/current before advancing the cursor; a failure of the second lane
cannot credit the first. The final single tile and odd windows are supported.

The live receiver/protocol/submission gate and actual pool target remain as
before. One connection, 300 seconds maximum, at most one new custom share,
no automatic reconnect or retry. Status reports remain distinct from shares.
`--two-streams` requires `--cache-a`; default remains the existing one-stream
backend. Worker/agent identify v042 and report the selected backend truthfully.
No continuous service is installed. XMRig, clocks and service definitions stay
unchanged; the external Termius wrapper temporarily pauses/restores WildRig.

Installer checks all pinned dependency manifests, local CPU library and the
completed v041 correctness/performance report. It then runs a NEW offline gate:
fresh synthetic GPU commitment -> nonce -> candidates from both streams -> new
V3 proof -> official CPU verifier; retained buffers across two miss windows;
odd splits; final single tile; job replacement immediately after first launch
must drain it and earn zero cursor credit; stale proofs are rejected. Only a
complete successful gate enables the bounded live run. Earlier GPU kernel
correctness/benchmark suites are not repeated.

Host tests cover pair ownership/cursor atomicity, global IDs, stale launches,
queue failure, resource cleanup, runner selection and installer gates. These
are orchestration tests, not pool acceptance evidence. Genuine custom pool
acceptance remains unproven until an actual submitted share is accepted.

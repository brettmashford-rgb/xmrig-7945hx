# V083: native dispatch and CUDA Graphs over unchanged pair-direct

Architecture target 3, first bounded host-dispatch screen. V082 retained pair-direct at approximately 2,374,659 tiles/s, 79.60 W and 29,543 tiles/J. Sharing B improved the matching two-nonce block by 4.52%, but was still 3.49% slower than pair-direct and approximately 0.27% less efficient. V083 changes no GPU arithmetic or traversal.

## Modes

| Mode | Per-16K submission and completion | Kernel | Snapshot/guards |
| --- | --- | --- | --- |
| pair-direct | Existing Python reset, scanner, collector, wait and readback | Existing a_pair_direct_scan, 256 threads | Existing 504-byte snapshot, all 28 endpoints |
| native-direct | One Python-to-C call performs those five driver calls | Same function and arguments | Same complete snapshot and Python guard/CPU decoder |
| native-graph | One Python-to-C call updates two graph nodes, launches the graph, waits and reads back | Same function and arguments | Same complete snapshot and Python guard/CPU decoder |

The native bridge is ordinary C11 and builds with the rig's existing GCC. It needs no CUDA headers, toolkit or CUDA linker library. Verified C source is compiled into a new experiment-local shared library; its source hash, command and resulting library hash are recorded. The bridge receives the already-loaded CUDA driver's function pointers. C/ctypes ABI sizes are checked before any native dispatch.

The graph has three explicit dependencies: clear status -> scanner -> guard collector. It is instantiated once per nonce/dispatch. Both scanner and collector node parameters are refreshed before every launch, including first/count, generation, audit, capacity and grid. Reset always clears exactly eight bytes. The raw v1 graph entry points use CUDA_KERNEL_NODE_PARAMS_v1 and CUDA_MEMSET_NODE_PARAMS_v1; the wrapper intentionally does not apply the SDK's newer v2 function-name macros. Graph executable and source graph are destroyed after draining and before their buffers are freed.

This moves one bounded batch's driver sequence into C. The nonce loop, planning, cursor accounting, candidate verification and proof creation remain Python. It is not a full native miner worker or a persistent GPU search loop. The native graph still performs two host-side node updates each batch; graph launch is not assumed cheaper.

## Unchanged kernel and correctness

All modes load the already-installed, hash-verified V080 PTX, SHA256 `99f53e9f0ae22496b8bf8348b24448060d50cc5d4440ee41a4d2ac04923bf0bf`, and use its actual pair-direct entry and collector. No new PTX is generated or substituted. The 16x2 layout, six MMA instructions, four K32 steps/stage, 256 K128 checkpoints, query mapping, nonce A/key, target tests and queue semantics are unchanged.

Native C copies the entire 504-byte snapshot only after its stream finishes. The existing decoder receives exactly those bytes, validates every guard and generation/window identity, then reads any populated candidate queue or requested audit words through the existing path. Candidates retain independent CPU verification. A failed driver call reports its phase; pending work is drained before cleanup. Native calls are bounded to one 16K batch: a job change during the call can allow that in-flight batch to finish, but post-call generation checks prevent stale result/cursor credit.

Each mode must pass fresh rig gates before timing: two production nonces, eight audited 16K transcript windows checked by canonical ID against independent V070 GPU results, sixteen CPU transcript samples, target/equality cases, partial populated overflow, full 16K zero-capacity overflow, all 28 corrupted guard endpoints, invalid maps, retained/stale ownership, odd-column windows and two fresh V3 proofs verified with the official CPU verifier. These are offline checks, not accepted pool shares.

## Separate host/GPU profile

A dedicated pair-direct search performs 32 instrumented 16K windows before speed timing. It records exclusive host time in reset, launch API, stream wait, readback and bookkeeping buckets. CUDA events bracket the actual scanner on its stream. Event instrumentation is reported separately. This search and its resources are closed before the comparison searches are built.

GPU event intervals overlap host waiting and must never be added to the host buckets. They may contain scheduling or submission gaps; they are not instruction-cycle counts or achieved Tensor Core utilization. The profile is a diagnostic for remaining host overhead. It does not forecast a speedup, and its instrumented observations are excluded from throughput and energy trials.

## Equal work and power

Twelve balanced rounds cover all six mode orders twice. Each mode processes the same fresh nonce and exact canonical intervals, 524,288 tiles/round and 6,291,456 unique timed tiles total. Initial setup/JIT/graph instantiation and telemetry are excluded; setup is reported separately. Preference requires more than 3% lower median elapsed than the existing Python control.

Driver diagnostics process 32 additional 16K windows per mode. The Python control requires 32 resets, 64 launches, 32 waits and 32 complete 504-byte readbacks, without search uploads or context-wide synchronization. Native-direct performs the same calls inside C. Native-graph requires 64 node updates, 32 graph launches, 32 waits and 32 complete readbacks. Native C counters report internal calls explicitly: absence from Python's API wrapper is not treated as absence of driver work.

Automatic read-only NVML samples run at 200 ms. Two balanced rounds each condition one full nonce then measure three fresh full nonces per trial: 50,331,648 measured tiles per mode. Energy includes nonce preparation, A setup, native/graph construction, full search and cleanup; initial job/base/B/maps setup is excluded. Approximate board energy is not wall-plug energy. Unsupported sensors preserve valid speed results and mark efficiency unavailable.

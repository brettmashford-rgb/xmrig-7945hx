# v080: tune the paired-column winner's B-stage depth, then test the selected mode live

V079 selected pair-direct: 2,340,456 median tiles/s versus 2,091,126 for wide16k (+11.92%), 84.5 W versus 93.9 W approximate GPU-board power, and 27,698 versus 22,106 tiles/J (+25.30%). Shared A staging was slower and less efficient than the matched direct variant. V080 retains the actual V079 direct-A paired kernel as the control and changes only the K32 B-stage depth in two candidates.

| Mode | Entry | K32 steps/stage | K span/stage | Static shared arrays |
| --- | --- | ---: | ---: | ---: |
| pair-direct | Actual unchanged a_pair_direct_scan | 4 | 128 | 10,240 bytes |
| pair-step2 | pair_step2_scan | 2 | 64 | 8,192 bytes |
| pair-step8 | pair_step8_scan | 8 | 256 | 14,336 bytes |

All modes use 256 threads, the same 16-row-axis x 2-column-axis layout, four tiles' accumulators/transcripts per consumer warp, direct A loads, identical targets and guarded 16K dispatches. The four-step entry and guard collector are byte-identical to the previous module. The included shared-A variant is not selected by any V080 mode.

The candidates parameterise a copy of the V079 body with ShareA fixed false. The B producer loops over step=warp%4, adding four until the configured stage depth is covered. The two-step variant uses two producers per column; the eight-step variant has each producer build two steps. A depth-aware fragment index separates both columns' buffers. Consumers read steps in the original increasing K order. All warps retain validation/barrier participation, including inactive consumers and an absent final paired column. Exact six-MMA arithmetic, cumulative accumulators, K128 checkpoint/fold/emission, A bounds, queue/guard/generation semantics are retained. Two-step staging still emits checkpoints every K128 (across two stages); eight-step staging emits both required checkpoints inside its K256 stage. No checkpoint is omitted or reset at a stage boundary.

This trades shared storage and production scheduling against block synchronization frequency. It does not assume that fewer barriers or a larger stage is faster. Native registers, local memory and maximum block/warp residency are reported on the rig.

## Validation before timing

Each mode independently runs two fresh production nonces, eight full 16K audited transcript windows by canonical ID against v070, sixteen independent CPU matrix/transcript samples, target/queue cases, populated partial overflow, full-16K zero-capacity overflow, all 28 guard endpoints, invalid maps, retained/stale ownership and two fresh V3 proofs checked by the official CPU verifier. Each also runs the established 160x110 odd-column profile (six windows, two CPU samples), covering a second-column-only request and a final unpaired column. All three modes must pass before timing or pool connection.

Source contracts compare the entire candidate body to the original with only the explicit stage-depth, producer-loop and fragment-index substitutions. PTX checks the real 24-argument ABI, six MMA instructions, barriers and static shared sizes, plus byte-identical control and collector entries. Compiled C++ tests under undefined-behaviour sanitizer exhaust stage production/consumption across all K positions for depths 2/4/8, prove no fragment alias/omission, check four-step index compatibility, final physical A-row addressing and all 256 checkpoints at precisely K128 increments. The unchanged full-production mapping/A-operand regression contracts remain included. Host tests cannot execute a GPU.

## Offline comparison

Twelve balanced rounds cover all six mode orders twice. Each round processes the same 524,288 canonical tiles in the same paired traversal; 6,291,456 unique timed tiles per mode. Initial setup/JIT and telemetry are excluded; setup is reported. A separate diagnostic requires 32 resets/waits/504-byte readbacks and 64 scanner/collector launches per mode, with no search HtoD or context-wide synchronization. A candidate is promoted only if its median elapsed time is more than 3% lower than the actual four-step pair-direct control. The eight/two-step ratio is diagnostic.

The read-only NVML phase runs before live connection: 200-ms sampling, two balanced rounds, one conditioning plus three measured complete nonces per trial, 50,331,648 measured tiles per mode. It includes fresh nonce/A preparation, search and cleanup, excluding initial job/base/B/geometry preparation. It reports approximate GPU-board energy, clocks, activity, temperatures and limiting flags. Unsupported sensors leave speed usable and explicitly mark energy unavailable. These are controlled offline board-energy measurements, not wall-plug or live-pool efficiency. Activity percentages do not establish Tensor Core or bandwidth saturation or achieved occupancy.

## Bounded live test

After all fresh gates and offline comparison complete, the same launcher automatically uses the preferred stage mode for one live attempt of up to five minutes. If neither candidate clears the threshold, it uses the existing four-step pair-direct winner. The mode is printed before connection and recorded in mining-result.json. The live factory is tools.pair_depth_scan.new_search with that exact mode and 16K advances, cached nonce frontier, job B tables and resident geometry. It never silently falls back to the old wide16k/v066 backend.

The rig's saved independent login supplies the wallet; no wallet or capture is embedded or uploaded. The established pool endpoint, actual target and V3 submission protocol are retained. The run permits at most one freshly checked custom share, with no reconnect, share retry or captured-share replay. A report_info acknowledgement is distinct from an accepted share. Pool acceptance is established only by a correlated accepted-share response. A completed zero-share attempt remains a live work/throughput observation. Live power is not separately sampled.

LIVE SUMMARY reports the selected mode, completed tiles/full nonces, actual elapsed time, whole-attempt tiles/s, stage durations, joined worker, shares sent/accepted and separate accepted status-report count. Whole-attempt throughput includes preparation and connection overhead. Scripted-pool host tests validate mode propagation, 16K advances, nonce rollover and owner retention, fresh proof submission/correlated verdicts, status acknowledgements, cleanup failures and invalid selection/flags for every mode. Mock responses are not actual pool acceptance.

# v0.0.35: reusable dispatch buffers and deduplicated descriptors

The v34 rig profile attributed 0.2601 s of the virtual path's 0.3844 s to
Python/bookkeeping over eight 4096-query scans. Fragment scanning had a shorter
GPU event interval (0.07746 versus 0.10879 s), but 0.6367 s of Python/bookkeeping
and 0.7312 s wall time. Cooperative scanning was slower on both clocks. These
are synthetic component measurements, not mining throughput or accepted shares.

The new explicit PreparedDispatch backend leaves GPU math, noise inputs, target
comparison, candidate format, and pool code unchanged. It allocates bounded,
guarded descriptor/target/status/queue/audit buffers once; retains the kernel
function and ctypes argument storage; and uploads descriptors and targets only
when the prepared batch changes. Every launch resets status and updates its
64-bit generation. Per-run capacity can shrink within the allocated queue limit.

QueryPacker validates and serializes unique global row/column tuples, preserves
query order and duplicates, and retains original global queries for candidate
verification. Cached rows map to the existing immutable fragment cache. Each
axis cache is capped at 4096 entries. Tuple identity reuses prior validation;
equal but distinct tuples still receive strict type checks, including rejecting
booleans that would otherwise compare equal to integers. Packed bytes are tested
against the established serializer for global and mapped indices.

Complete returned hits still receive independent CPU math checks. Partial queues
remain overflow results requiring retry, with no CPU validation credited. All
dispatch and source-cache guards remain active. Optional generation callbacks
reject work before launch, after GPU completion, and after CPU validation. The
backend owns only its dispatch allocations and requires an open source cache.
It is not selected by the live miner in this release.

The offline GPU harness checks eighteen new dispatch target/queue cases against
independent CPU references, then compares all 4096 transcripts across original
and prepared variants of three already-validated kernels. Eight rotating rounds
measure repeated input dispatches. A second comparison uses eight disjoint
1024-query windows (8192 distinct tiles per path), including each prepared
window's host packing and uploads in its measured time. No target is relaxed
for timing; timing uses synthetic zero targets. Correctness cases explicitly
exercise maximum and equality bounds.

A representative 768-query cover materializes rows needed by all windows:
88,080,384 bytes, below the existing 128-MiB cap. Dispatch setup, initial batch
preparation, noise setup and materialization are reported separately. Summary
with_setup includes dispatch setup and, for fragment/cooperative paths, cache
materialization. Repeated summaries also include initial batch preparation.
Noise setup is common and reported separately. Correctness/warmup overhead is
outside timing. Changing-window timing uses a warmed serializer from validation
and repeated comparisons; it does not establish cold-start production speed.

GPU event intervals overlap host waiting and are never added to host wall time.
Each measured prepared scan must make zero device-allocation calls. The full
private report preserves per-round host categories and API counts. Only
synthetic seeds enter this experiment; no live jobs, pool IO, proofs or shares.
Existing source/PTX and the CPU library are verified/reused without recompiling
or redistributing native code. GPU validation and speed results are pending the
rig test. Host tests cover serialization, ownership, partial/complete queues,
status reset, changing batches, high-bit generation values, stale generation
callbacks, buffer guards and complete disjoint grid coverage.

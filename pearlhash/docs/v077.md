# v077: register pressure / residency comparison, then a bounded live pool test

V076 retained wide16k. Its control measured 2,101,146 median tiles/s and 22,232 tiles/J at 93.5 W GPU-board power. Four/eight-step scheduling gained only 0.57%/0.10% speed, used 104 rather than 96 registers/thread, retained two resident blocks/SM, and lost efficiency. Scheduling was not promoted.

V077 keeps the winning 256-thread CTA8 arithmetic and its 16K host dispatches. Two candidates apply CUDA launch-bounds compiler residency requests to an exact copy of the original body. There is no consumer unrolling change. The compiler may reduce registers, add instructions or spill; requested residency is not a guarantee of achieved occupancy or speed. Actual JIT registers, shared/local memory and maximum active blocks/warps are reported by the existing resource diagnostic.

| Mode | Kernel entry | Threads | Compiler minimum-block request |
| --- | --- | ---: | ---: |
| wide16k | cta_b8_scan | 256 | Original control |
| wide16k-resident3 | wide_resident3_scan | 256 | 3 |
| wide16k-resident4 | wide_resident4_scan | 256 | 4 |

The candidate bodies preserve the exact source arithmetic, A pointer bounds, all six MMA instructions per K32 step, eight-step B production, all K128 cumulative checkpoints, transcript folds/emission, targets, queue semantics, map validation and barriers. Separate template instantiations isolate their shared-memory symbols. Host tests require both exact copied-body equality and byte-identical compiled control/snapshot entries versus the previous release. PTX tests check both launch-bounds directives and the unchanged 24-argument ABI.

All three modes independently pass fresh rig gates before timing: two production nonces, eight 16K transcript windows against v070 by canonical tile ID, sixteen CPU transcript samples, target cases, partial and full-16K overflow queues, all 28 guard endpoints, invalid row/column maps, retained/stale ownership and two official CPU-verified V3 proofs per mode. Failure blocks timing and live mining.

Speed timing retains twelve balanced rounds across every mode order, 524,288 identical canonical tiles per mode per round, and 6,291,456 distinct timed tiles per mode. Setup and telemetry are excluded; driver calls/readback bytes are checked in a separate instrumented pass. Promotion requires more than 3% median elapsed reduction against the original wide16k control. The candidate4/candidate3 speed ratio is diagnostic.

The same launcher then performs the unchanged approximate GPU-board energy trials: 200-ms NVML sampling, two balanced rounds, one conditioning nonce and three measured full nonces per trial, 50,331,648 measured tiles per mode. Energy includes nonce preparation, A setup, search and cleanup, excluding initial job/base/B/geometry preparation. Clock, activity, temperature and throttle flags are reported. These are offline GPU-board measurements, not wall-plug energy or live-pool efficiency. Kernel-active percentage does not establish Tensor Core saturation or achieved occupancy.

## Live stage

After all offline gates and the comparison complete, the launcher automatically runs one live attempt of up to five minutes. It chooses the promoted candidate, or the original wide16k if neither candidate clears the threshold. The selected mode is printed before connection and recorded in mining-result.json. The live runner uses the actual v077 factory, 16K advances, the selected entry, cached nonce frontier, job B tables and resident geometry. It does not fall back to the old v066 scanner. Scripted-pool host tests check mode propagation, 16K advances, complete-nonce rollover, retained owners, cleanup failures, fresh candidate/proof submission and correlated response handling for all three modes.

The saved independent login on the rig supplies the wallet; no wallet or captured login is added to this repository. The existing pool endpoint and V3 submission protocol are retained. Actual share target is unchanged. The attempt permits at most one freshly checked custom share, with no reconnect or submission retry. A status-report acknowledgement is not counted as an accepted share. An attempt without a share remains a live work/throughput observation; pool acceptance is established only by a correlated accepted-share response. Stage totals and whole-attempt completed-work accounting include preparation costs. Live power is not separately sampled; the power comparison precedes the connection.

The installer verifies all 40 prior dependency packages, the v075/v076 suites and retained baseline, then installs separately to /home/user/pearlhash-dev-v0.0.77. The launcher pins the installer; the installer pins an immutable source commit and package hashes. It stops pearl.service for the run, applies a 2,100-second overall timeout, and restarts WildRig on exit, with a 40-minute recovery timer. No permanent service, clock, CPU-miner or autostart changes are made.

Send REGISTER RESULT, POWER RESULT, KERNEL RESOURCES, LIVE RESULT and Stage totals. Reports: /home/user/pearlhash-dev-v0.0.77/register-comparison.json and mining-result.json. Log: /home/user/pearlhash-v077-launch.log.

Development validation: 117 relevant host tests passed, including the new compiled/source contracts, all-mode queues/lifecycle, benchmark/telemetry orchestration, installer gates, scripted live pool tests, winner-to-live selection, worker and work accounting. Two NVRTC 12.9.86 compute_120 builds were byte-identical. Rig GPU execution, official proof verification, native register/spill/residency results, speed/power and actual live-pool acceptance remain pending.

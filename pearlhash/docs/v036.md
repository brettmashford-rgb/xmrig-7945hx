# v0.0.36: reusable virtual dispatch in the bounded live worker

The v35 RTX 5060 test passed eighteen CPU transcript/target/queue cases and the
full 4096-query transcript comparison. Across eight disjoint 1024-query windows,
virtual scan wall time fell from 0.137694 to 0.058665 seconds; dispatch setup
brought the latter to 0.060854 seconds. Fragment scanning was 0.046998 seconds,
but 0.148922 seconds with setup/materialization. The selected backend is therefore
the reusable virtual path. These are component results, not miner throughput.

PreparedCandidateBackend connects the verified v35 PreparedDispatch to the existing
NonceSearch and WideRangePlan without changing global tile order or IDs. One nonce
owns one VirtualTables noise cache, one five-buffer guarded dispatch set, one
prepared batch and a bounded descriptor-axis cache. Every changing window prepares
and uploads new descriptors/targets. Overflow retries retain the same prepared
batch and change only queue capacity/status/generation arguments. A different
nonce gets fresh caches. The backend rejects a generation change within its own
lifetime. The job-current callback raises StaleWork before launch, after completion
and after candidate CPU checks. Outer range and submission gates remain intact.

The actual pool target, V3 seed binding, nonce preparation, independent candidate
math/proof construction, submission format and correlated response handling stay
unchanged. Only complete returned hits receive CPU checks; misses are not
recomputed by the search. A cancelled batch cannot advance the committed cursor.
Closure frees dispatch buffers before noise buffers and reports aggregate counts;
no raw job data is added to lifecycle telemetry. The report labels the new backend,
and the login worker/agent identify v036. The receiver remains active during CPU
and GPU work, with a single latest-job mailbox and no automatic reconnect.

The installer requires the completed v35 GPU report and verifies installed
v35/v33/v31/v27/v17 manifests and the local CPU library against the already-installed
v31 manifest. It installs readable Python sources, with no new native download or
GPU compilation. The package includes the existing pool modules to keep their
Python package resolution explicit.

Before any live connection, a new synthetic 160x192 K32768/rank128 job uses the
production 10x16 patterns and a near-maximum synthetic scaled target. One fresh
nonce goes through the new backend, independent proof construction and the existing
official offline CPU verifier. A separate tiny-target job checks two resumable
windows retain buffers, then target replacement closes stale search/proof stages.
Those synthetic targets are confined to the offline check; live targets are never
changed. The offline proof is not submitted.

Only after that preflight passes, the launcher runs one bounded connection to the
previously configured pool.pearlhash.xyz:9000 for up to 300 seconds, at most one
fresh custom share and no automatic retry. Saved wallet credentials stay local.
No copied/captured share is submitted. The assigned-extranonce role remains a
hypothesis until a genuine custom share is accepted. A dashboard/status-report
ACK is not a mining-share acceptance.

The shell stops WildRig only for this test and restores it afterward, with a
15-minute fallback restart timer. XMRig, service definitions, autostart and clocks
are untouched. The live Python runner changes no services itself. In-flight
native CPU calls must finish on cancellation. No continuous service is installed.

Host validation includes four fake-driver backend integration tests, five existing
reusable-dispatch tests, six persistent cursor/cancellation tests and three mocked
bounded-miner orchestration tests. Mock share verdicts test plumbing only and do
not establish pool acceptance. GPU proof validation and real live results remain
pending the rig run. No new miner-throughput, efficiency or accepted-share claim.
